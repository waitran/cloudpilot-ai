# Безопасность и эксплуатационные ограничения

На этапе 1 реализованы явный CORS, скрытие credentials в ошибках конфигурации,
безопасный формат API-ошибок, генерация приватного локального .env и non-root контейнеры приложения.
Safety Controller и разрешения на инфраструктурные действия ниже остаются требованиями будущих этапов.

## Доступ и секреты

- Отдельные read-only credentials для сбора и минимальные права исполнителя.
- Изолировать проекты/тенанты, проверять принадлежность ресурсов в API и worker.
- Секреты передаются через окружение/secret store; в Git разрешены только пустые шаблоны.
- Исключить токены из логов, аудита, prompt и ответов модели; редактировать чувствительные поля.
- Начальный репозиторий должен быть private. Доступ к исходникам не даёт права менять production.

## AI и недоверенные входные данные

Метрики, названия ресурсов, логи и пользовательский текст — недоверенный ввод.
Инструкции из них не меняют политики. Разрешённые инструменты имеют фиксированные
типизированные параметры, проверяются сервером и не включают произвольный shell/kubectl.
LLM не получает write credentials; prompt injection не должен открывать путь к исполнению.
Для внешних API нужны allowlist адресов, ограничения исходящих запросов, размера ответа и таймауты.

## Применение и восстановление

Перед записью проверять точную ревизию плана, срок approval, свежесть данных, дрейф,
квоты и готовность резерва. Вести аудит «кто, что, зачем, когда», idempotency key
и события переходов состояния. Должны быть kill switch и предел допустимых затрат.

Canary требует порогов SLO, окна наблюдения, критериев остановки, сохранённого baseline,
проверенного плана восстановления и ресурсов для его выполнения. Rollback может не сработать
из-за внешнего сбоя или недоступности мощности: такие ошибки требуют эскалации и явно видимого
статуса. Нельзя обещать гарантированное восстановление. Необратимые изменения данных исключить
из раннего набора действий.

## Текущая защита репозитория

`.gitignore` исключает локальные секреты и данные. `scripts/check_repository.py`
проверяет опасные имена, известные формы токенов, приватные ключи и credential URL
в рабочих файлах и отдельно в индексе Git. Значение найденного секрета в ошибку не выводится.
Эвристика не доказывает отсутствие всех возможных секретов и не заменяет ревью,
secret scanning или отзыв скомпрометированного ключа.

CI получает только `contents: read`, использует закреплённые SHA Actions,
не сохраняет checkout credentials и не обращается к облаку. Платные облачные операции
и нагрузочные тесты production требуют отдельного разрешения.
