# Предварительная архитектура

Все компоненты ниже запланированы. На этапе 0 их исходного кода нет.

## Поток рекомендации

1. Backend принимает требования: бюджет, требуемую экономию, p95/p99, error rate,
   throughput, availability, горизонт и профиль нагрузки, разрешённые действия.
2. Data Collection сохраняет нормализованный снимок с временным диапазоном, источниками,
   свежестью, пропусками и единицами измерения. Цены имеют валюту и дату действия.
3. Feasibility Engine проверяет полноту условий и грубую выполнимость. Capacity Planner
   рассчитывает резерв и ограничения размещения. Optimization Engine строит кандидатов.
4. Для каждого кандидата выполняются финансовая оценка и проверки ограничений.
   Статусы: `insufficient_data`, `infeasible`, `candidate`, `validated`, `rejected`.
   Нельзя объявлять математическую невыполнимость только по неудачному перебору эвристики.
5. Optimization Lab сравнивает baseline и кандидата на одинаковом сценарии нагрузки.
   Измерения, версия сценария и отклонения сохраняются. Отчёт содержит область применимости.
6. Пользователь видит план и подтверждает конкретную ревизию. Safety Controller повторно
   проверяет свежесть, доступную мощность, политики и условия отката.
7. Разрешённый план выполняется canary-процессом. По нарушениям порогов или потере наблюдаемости
   расширение останавливается; запускается предусмотренное восстановление.

AI может предложить требования или объяснение, но не подменяет цены, метрики и решения контроллера.
Невыполнимую цель нельзя «выполнить» ослаблением SLO без решения пользователя.

## Данные и выполнение

На старте — PostgreSQL как единое хранилище и модульный монолит с явными границами Python-модулей.
Планируются сущности: Project, DataSnapshot, RequirementsRevision, Candidate,
Experiment, Evaluation, ChangePlan, Approval, Execution и AuditEvent.
Это черновик модели, не готовые таблицы или API-контракт.

Длительные сборы и эксперименты выполняет отдельный процесс worker из той же кодовой базы.
Конкретный механизм очереди выбирается при появлении фоновых задач. Kubernetes Jobs изолируют
нагрузочные эксперименты; отдельный кластер для приложения на этапе 1 не требуется.

## Масштабирование

- HPA меняет число pod в пределах ограничений. Он не создаёт ноды и не обеспечивает
  сам по себе доступную мощность.
- Capacity Planner учитывает requests, DaemonSets, allocatable, affinity/taints,
  topology spread, PDB, квоты, лимиты IP и время старта новых нод.
- Cluster Autoscaler либо Karpenter выбирается по провайдеру. Capacity Guard проверяет
  максимумы node pools, облачные квоты и совместимые типы/зоны инстансов.
- Альтернативные инстансы допускаются только при совместимости архитектуры CPU,
  памяти, дисков, сети и требований приложения; Spot не считается надёжным резервом сам по себе.
- При невозможности размещения нельзя продолжать уменьшение мощности. План отклоняется,
  текущая рабочая конфигурация сохраняется и показывается причина.

Резерв оценивается по данным и сценариям. Конечные тесты не гарантируют работу при любой
будущей нагрузке; неизвестные условия должны быть явно отражены в отчёте.

## Границы MVP

Сначала один явно выбранный Kubernetes-провайдер и read-only анализ. Универсальная поддержка
всех облаков, собственный оператор и набор микросервисов не входят в начальный объём.
До появления Safety Controller и подтверждений внешняя запись запрещена.
