# Этап 3. Сравнение конфигураций

Откройте **Recommendations**, выберите VM или Kubernetes Pod и нажмите **Run analysis**.
Эта же форма доступна из карточки ресурса через **Analyze sizing**. Анализ читает
inventory и метрики из PostgreSQL в одном снимке. Отчёт можно скачать как JSON вместе
со временем расчёта, версией политики, исходной конфигурацией, статистикой и введёнными тарифами.

## Метрики и размеры

- Для VM базой служат CPU/RAM capacity, для Pod — requests. Лимиты Pod учитываются при отборе.
- Нужны свежая запись inventory и семь дней измерений CPU и RAM. Каждая метрика
  должна иметь один источник, постоянный интервал от 15 до 3600 секунд, свежесть
  до 15 минут и отсутствие разрывов длиннее полутора интервалов. Начальную границу
  может покрыть ближайший предшествующий замер. При ошибках или нехватке данных
  отчёт показывает конкретную причину.
- Профили Lean, Balanced и Conservative добавляют к измеренному пику 15%, 30% и 50%.
  CPU округляется вверх до 0,01 ядра, память — до 16 MiB. Минимум для Pod составляет
  0,05 ядра и 64 MiB, для VM — 1 ядро и 512 MiB. Повторяющиеся варианты и исходный
  размер исключаются. p95 рассчитывается методом ближайшего ранга по выборке
  и приводится для контекста. Размеры рассчитываются от пика.
- Отдельный Pod оценивается в пределах его UID. Анализ Deployment/StatefulSet
  требует агрегирования наблюдений по репликам. Окно текущего анализа заканчивается
  последним замером, поэтому после перезапуска нового Pod требуется его собственная история.
- Предложенные requests и размеры VM требуют проверки размещения и SLO под нагрузкой.
  По данным этапа 3 нельзя подтвердить производительность предложенной конфигурации.
  Разница CPU/RAM показывает изменение запрошенной или выделенной мощности.

## Стоимость VM

При наличии сопоставимых тарифов включите **Compare manually priced VM offers**.
Введите источник расценок с датой, валюту, одинаковое количество оплачиваемых часов
(1–8760) и до 20 альтернатив. Используйте одинаковую область, модель оплаты и предположения
о нагрузке. В recurring extras укажите стоимость дисков, сети, обязательств и других
регулярных расходов за весь период. В transition укажите разовые расходы на миграцию,
валидацию и прочие работы по переходу, если они применимы.

- Текущая стоимость = текущий почасовой тариф × часы + текущие регулярные расходы.
- Стоимость варианта = его почасовой тариф × часы + его регулярные расходы + переход.
- Экономия = текущая стоимость − стоимость варианта. Отрицательная экономия показывает
  увеличение затрат. Процент доступен при положительной текущей стоимости.

Отчёт показывает до пяти предложений, которые покрывают наблюдаемый пик плюс 30%
по CPU и RAM. Они упорядочены по полной стоимости за выбранный период. Суммы рассчитываются
через Decimal и передаются строками в одной валюте. Размеры памяти в ответе тоже передаются строками. Тарифы VM задаёт оператор.
Исторические записи Billing остаются доступны из карточки ресурса. Для сценариев
без тарифов и для Pod денежные поля пусты. Экономия на инфраструктуре Kubernetes
потребует отдельной оценки оплачиваемых нод и условий договора.

API `POST /api/v1/optimization/resources/{resource_id}/analyze` принимает `{}`
для расчёта размеров и объект `pricing` для оценки VM. Контракт доступен в Swagger
на `/docs`. Статусы результата `candidates`, `no_candidates`, `insufficient_data`
и `unsupported_resource`. Синтетические источники помечены в отчёте.
