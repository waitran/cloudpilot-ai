# Этап 4. Проверка размещения Pod

Откройте **Capacity planning** или выберите **Check placement** у варианта Pod
на странице Recommendations. Вторая кнопка переносит предлагаемые CPU и RAM.
Для пробного запуска выберите **Load synthetic example**, затем **Check capacity**.

В расчёт входит пиковое число **дополнительных** одинаковых Pod. Для обновления
старые реплики, которые ещё работают одновременно с новыми, учитываются в занятых
ресурсах и остатках квот. Для HPA передайте разницу между необходимым и уже учтённым
числом реплик. CPU задаётся в millicores, память — в байтах.

## Снимок

Запрос `POST /api/v1/feasibility/evaluate` принимает один сценарий. Полная схема
и типы доступны в Swagger через `/docs`. Снимок заполняет оператор. Он может
подготовить значения из Kubernetes и панели провайдера или использовать
явно помеченный синтетический сценарий. Снимки старше 15 минут отклоняются.

| Поле | Что передать |
| --- | --- |
| context, namespace, observed_at, synthetic | Имя кластера, namespace, время сбора с часовым поясом, происхождение данных |
| nodes[].allocatable | CPU, RAM и лимит количества Pod, доступные для размещения на каждой ноде |
| nodes[].occupied | Сумма эффективных requests и занятые слоты всех учтённых Pod |
| nodes[].eligible | Подходит ли нода для этого Pod с учётом готовности, cordon, labels, taints и применимых правил |
| inventory_complete | Покрыты все подходящие ноды и уже занятые ресурсы |
| constraints_reviewed | Для точной спецификации Pod учтены применимые admission и scheduler ограничения |
| namespace_quota | Подтверждённые остатки применимых квот. Пустой объект означает подтверждённое отсутствие лимитов, null — неизвестное состояние |
| pod_ips_remaining | Число свободных адресов, подтверждённое для рассматриваемых вариантов размещения |
| pools[].allocatable, daemon_requests | Доступные ресурсы и эффективные requests и слоты DaemonSets на каждой новой ноде |
| pools[].scale_limit_remaining | Сколько нод ещё позволяет добавить ограничение пула |
| pools[].provider_nodes_available | Подтверждённый остаток с учётом квот, наличия инстансов и адресов нод. null означает отсутствие подтверждения |
| pools[].ready_within_seconds | Верхняя оценка выхода всей рассматриваемой группы нод в готовность при параллельном старте, включая сетевые и обязательные системные компоненты |
| pools_complete | Учтены все доступные пулы для заданных ограничений |
| failure_load_accounted | В occupied и daemon_requests учтён консервативный расход на переселение существующих нагрузок при отказе. Требуется при проверке потери нод |

Если квота считает limits, укажите эффективный limit Pod. Значение после мутаций
admission и requests для init, sidecar и overhead должны уже входить в снимок.
Правила, зависящие от совместного размещения нескольких реплик, например topology
spread, pod anti-affinity и привязка PVC, могут сделать бинарную отметку eligible
недостаточной. В таком случае оставьте constraints_reviewed=false. Значение true
уместно, если известные ограничения учтены консервативно, в том числе сетевые IP
для конкретных зон и пулов. Сценарий предполагает одинаковую спецификацию всех новых Pod.

## Решение

Из allocatable каждой ноды вычитается резерв CPU и RAM в процентах и уже занятая
мощность. Локальное число дополнительных Pod ограничено минимумом из трёх величин.
Это число Pod по CPU, по RAM и свободные слоты. Подходящие ноды суммируются только
после этой проверки, поэтому разнесённые по разным нодам CPU и RAM не образуют
один пригодный слот. Из доступных слотов вычитается вклад заданного числа крупнейших
по пригодной мощности нод для проверки худшего заданного отказа.

Для каждого пула считается минимальное число дополнительных нод, подходящих
по форме, лимиту, предложению провайдера и сроку. Варианты взаимоисключающие.
Сначала показываются варианты с меньшим числом нод, затем с меньшим временем ожидания.
Время относится к подготовке мощности, запуск приложения и SLO проверяются отдельно.

| Статус | Значение |
| --- | --- |
| feasible_now | По снимку размещение возможно на существующих нодах с учётом заданного резерва |
| scale_out_required | Найдены варианты, при которых мощность появляется после добавления нод |
| infeasible | Подтверждённая квота или верхняя оценка общей мощности исключает сценарий при текущих условиях |
| insufficient_data | Не хватает подтверждённых данных для вывода |
| no_plan_found | Одиночные пулы не дали решения. Комбинация нескольких пулов может сработать |

Планировщик работает с переданным снимком и опционально проверяет потери нод
при заданном консервативном учёте чужой нагрузки. Расчёт размещения ограничен CPU,
RAM, количеством Pod и явно описанными квотами. Результат условный до повторного сбора
снимка, проверки реального Kubernetes и нагрузочного тестирования. Сам расчёт
не меняет кластер и не запускает autoscaling.

Справка по [Node Allocatable](https://kubernetes.io/docs/tasks/administer-cluster/reserve-compute-resources/),
[эффективным запросам Pod](https://kubernetes.io/docs/concepts/resource-management/effective-pod-requests-limits/)
и [квотам](https://kubernetes.io/docs/concepts/policy/resource-quotas/).
